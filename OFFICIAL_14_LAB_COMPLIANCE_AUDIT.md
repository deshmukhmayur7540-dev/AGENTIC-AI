Regression tests cover anonymous and Student denial plus out-of-scope generation. Plan history remains process-local. ## B. Source basis and status rules

### Official Build Book requirements used

Chapter 2 states that this worklet has one coordinator over three streams: notes/materials, assignment distribution and collection, and course project tracking. Its named workers are Notes Repository, Assignment Distribution, Submission Collection, Plagiarism/Similarity, Grading Assistance, Project Milestone Tracking, Faculty Review, and Grade Publishing & Archive.

The worklet's shared definition of done and gates include:

- A real request produces an organized, validated, evidence-grounded workspace based on faculty-approved rubric and syllabus.
- The coordinator owns an isolated run, locked plan, run state, budgets, and audit log.
- Course setup (notes, assignment briefs/rubrics, milestones) is approved before release.
- The validation gate checks: grade does not exceed rubric maximum; late submissions are correctly flagged; a similarity score is attached; and no grade is published without faculty approval.
- Validation is a hard gate. A bounded repair regenerates only the failing item; exhaustion escalates to course faculty.
- Faculty reviews, edits, overrides, and approves before a governed, versioned publish. Audit history and rollback are required.
- Similarity is a flag for human review, never an automatic finding of plagiarism. Submission timestamps are not altered. Notes retain version history.
- The faculty dashboard includes a versioned notes portal, submission on-time/late and similarity view, pending rubric-aligned draft grades, and project group milestone/checkpoint health.
- The pilot includes one versioned course unit, one full assignment cycle, a project with at least two checkpoints, and a submission dashboard.

Chapter 2 sections 2.1-2.12 also specify the agent roster, message map, canonical data entities, hybrid parallel/sequential execution, worked submission trace, risks/mitigations, guardrails, and 14 progressive increments. The matrix below paraphrases each lab's input/output, nodes, deliverable, acceptance criterion, and pitfall from section 2.10; it does not substitute repository-authored lab manuals for those criteria.

### Status interpretation

- **COMPLETE**: the specific incremental acceptance criterion in Chapter 2 is supported by implementation and test evidence. A complete early lab does not imply the complete capstone.
- **PARTIAL**: some implementation exists, but an explicit acceptance requirement is absent, disconnected, simulated, or insufficiently verified.
- **MISSING**: no meaningful implementation of that lab stage was found.
- **UNVERIFIED**: evidence is insufficient to classify implementation. This status is used for claims that cannot be established; it is not used to conceal known gaps.

`Implemented` means code exists; `simulated` identifies a demo/mock rather than a live integration; `verified` means the cited tests actually assert the described behavior. Tests do not establish deployment, real external service operation, or requirements beyond their assertions.
